# Implement

Step 4 of the spec-driven flow, in every tier; a small change starts here with its issue as spec. Small PRs reach main faster and get better reviews, so the default is **one ticket, one branch, one draft PR**. Never merge. The one exception is a small PR in a repo whose `conventions` allow it: it opens not as a draft and the agent only switches auto-merge on; see "Small PRs and auto-merge". Every subagent this skill dispatches starts with a fresh context window, never as a fork of this conversation.

## Mode

The argument after the issue picks the mode. No mode given and the spec has more than one ticket in this repo: ask once, before any branch, as a choice question with three options: "One PR per ticket (recommended)", "One PR for the whole spec" and "Stop before any branch", each with its consequence. One ticket, or fix-now rows from acceptance (step 2): no question; for fix-now rows the mode is the last PR's (a ticket checklist means `one-pr`). State the mode in the first line of the reply.

| | `per-ticket` (default) | `one-pr` (argument `one-pr`, "ein PR", "one PR") |
|---|---|---|
| PR unit | one ticket | all tickets of the spec in this repo |
| Branch | `gh issue develop <ticket>`, name `<prefix>/<ticket>-<slug>` | `gh issue develop <spec issue>`, name `<prefix>/<spec issue>-<slug>` |
| Base | the default branch; the open PR branch of its one unmerged blocker in this repo (stacked) | the default branch |
| Done state (resume) | per ticket: closed, or an open PR that closes it (its "Development" link can be missing) | the PR's ticket checklist |
| Links | `Closes #<ticket>`, `Part of #<spec issue>` | `Closes` for each done ticket of this repo, `Part of #<spec issue>` |
| When | the recommended answer | trying it out, or a wide refactor whose steps are not green on their own |

Call the Skill tool with "cj-project-context" for: commands, conventions, issue-tracker. Call the Skill tool with "cj-posting" before any outbound action. The user started this skill for PRs, so it carries the yes for the linked remote branches (`gh issue develop`), pushes to them, the PRs and their descriptions, switching auto-merge on or off as "Small PRs and auto-merge" says, assigning the unit's issue to the user and setting its board status as "Assignment and board status" says, deviation comments on the spec's issue, the `Tier: small, confirmed` comment after a small answer in step 1, and the restack in "After a merge"; every other outbound action needs its own yes. When a situation tempts you to bend a step, check [WRONG-TURNS.md](WRONG-TURNS.md).

Keep a TODO list with the harness's task tool: one entry per PR unit, each with its steps. Before the final report nothing is open, or the report names it with the reason.

## 1. Read and gate

- Input: the spec's issue, or one of its tickets (then only that ticket).
- Read the issue, its latest `## Spec` comment (or its body, when the body starts with `## Spec`) and every comment after it (deviations, answers, the latest `## Acceptance` comment), the sub-issues with their blocked-by edges and state, the applicable `AGENTS.md`, the glossary and the ADRs the spec names, and the affected code. Call the Skill tool with "cj-static-analysis" for the callers of the symbols the change touches; each unit asks again in its worktree before Build.
- **No spec** (no `## Spec` comment, no body starting with `## Spec`). The issue may serve as its spec for a typo or copy change, a fix that restores behaviour the issue states as intended (length alone does not disqualify it; step 3's size stop still applies), or a refactor whose issue states its scope and unchanged behaviour: say so in one line and go on with its criteria as AC-1… Before that line, such an issue, or a fix that only lacks its intended behaviour, whose change touches money, data, security or an irreversible step (judged by what it touches, not by words in the issue) settles its tier. The latest `Tier: <tier>, confirmed` line on the issue, from any comment, decides: small, go on; another tier stops as for a feature below, and so does a `## Challenge` comment, whatever the `Tier:` line. Neither: before any branch ask one question, as `cj-asking` says, naming the stake: go on as small, or first `/cj-grill-with-docs <issue>`; it shows the comment text a small answer posts. Small: post that comment, holding the line `Tier: small, confirmed`, without a second confirmation, and go on; a question about intended behaviour comes after, in its own message. Grill first: post nothing, no branch, name `/cj-grill-with-docs <issue>` and `/cj-to-spec <issue>`. A fix without its intended behaviour, or one of these with an open product decision: stop before any branch and ask the user as `cj-asking` says (call the Skill tool with "cj-asking"); go on only once the answer stands as a comment on the issue, posted through `cj-posting`; an answer that adds a new rule makes it a feature. A feature, a new rule the issue calls a fix, a fix mixed with a feature, or anything else: stop and name `/cj-grill-with-docs <issue>` and `/cj-to-spec <issue>`.
- The spec has an open question, or a criterion nobody can verify, not even through the open PR or by hand at acceptance: stop and ask. Code or docs answer facts; only product decisions go to the user.
- No sub-issues (the spec fits one ticket): the spec's issue is the one ticket; both modes give one PR. Leave its title unchanged, including any existing `[Epic] ` prefix. The PR only `Closes #<issue>`, without `Part of`.

## 2. Pick the work

First restack what "After a merge" describes. Then, per ticket of this repo, and for the spec issue in `one-pr`: `gh issue develop --list <n> --repo <its repo>`, and once `gh pr list --repo <this repo> --state open --json number,headRefName,closingIssuesReferences` (the PRs live in the code repo, even when the tickets live elsewhere); skip what the mode's done state marks as done. A linked branch without a PR is an interrupted run: `git fetch`, then continue in the worktree `git worktree list` shows for it, else `git worktree add <path> <branch>` as in step 3.1; never run `gh issue develop` for it again.

**Fix-now rows.** The latest `## Acceptance` comment has rows whose choice is fix now: they are this run's only PR unit, on the last open PR the comment names. Each row is an AC of the unit, the user's observation its bug report. `git fetch`, then continue on that PR's branch in the worktree `git worktree list` shows, else `git worktree add <path> <branch>`; never `gh issue develop`. Fast-forward it to `<remote>/<branch>`; diverged: stop and report. Run step 3 from Build on, a failing test first, written as Build says for a bug when the row describes one; step 8 replaces the row's earlier Verified line with one that cites the comment, `<row> (acceptance <comment link>): <evidence>, met`, rows with the same evidence sharing a line. A row is done, and skipped, once the Verified block cites that comment for it. That PR already merged: build nothing; `/cj-accept <issue>` turns the rows into follow-ups.

A ticket is **ready** when every blocker is closed, or (per-ticket) exactly one blocker is open, is in this repo and has an open PR, including one opened earlier in this run: that PR's branch becomes the base. In `one-pr`, a blocker inside the same unit counts as done once its commits are on the branch. A blocker in another repo that is still open, or two open blockers: not ready; the report says why and names `/cj-implement` in the other repo.

Done when you can state the PR units of this run, in blocked-by order, with the base of each.

## 3. Per PR unit

Finish one unit completely, PR included, before the next.

1. **Branch** through the issue the mode names, so it is linked under "Development": `gh issue develop <n> --repo <its repo> --branch-repo <this repo> --base <base> --name <name>` (prefix from `conventions`, else `agent/`). Check it out in its own worktree: `git fetch` and `git worktree add <path> --track -b <branch> <remote>/<branch>`, `<path>` from `conventions`, else the harness's, else a sibling directory of the checkout; the user's checkout only when they ask for it. Then tell the user once: `Worktree: <absolute path> (branch <branch>)`. `HEAD` equals `<remote>/<base>` before the first change. Never overwrite, discard or stash the user's uncommitted changes. The first unit of a spec also commits the glossary or ADR files the spec lists under "Recorded in repo"; the report tells the user to delete uncommitted originals in their checkout. Then, before Build, assign the issue and set its board status as "Assignment and board status" says; on a resumed branch too.
2. **Build** each ticket of the unit in blocked-by order. Tests first at the spec's seams where the project allows it. For a bug (a bug ticket, or a fix-now row that describes one), a fresh subagent writes the reproduction test before any fix; its prompt holds the repo and the report's symptom, steps, expected and actual result (for a fix-now row, the row and the user's observation), never a diagnosis or a fix, so suspected lines, code paths, proposed fixes and suggested tests in the issue stay out. The test is red before the fix; green means the bug is not reproduced: stop and report. No subagent available: write it yourself, and the PR's Risk line says so. Targeted tests and typechecks while working. Commit per finished step, self-contained, tests with the logic they cover, the repository's message convention, the ticket number in the message. **Mutation check**, for every AC test that covers a condition the diff adds or changes: on a clean, committed tree invert that condition once, run the test, restore; afterwards `git status` is clean again. The test must turn red. Green: a test is missing; write it before the PR and invert again. No input tells the inverted condition apart: the condition is dead; remove it instead. ACs without such a condition, such as copy or layout, get none.
3. **Size.** Over about 400 changed lines without tests and generated files: the ticket was cut too big. Say so and propose a split before going on; a preparatory refactoring becomes its own ticket.
4. **Deviations.** A technical decision that differs from the spec (interface, order, a module): a comment on the spec's issue, `Deviation: <decision> | <reason> | <cost if wrong>`, and continue. A change to behaviour, scope or an AC: stop and ask. On a yes, edit the spec comment as `cj-to-spec` describes under "Changing a posted spec" (that yes covers the edit).
5. **Checks.** The full required checks once on the unit's final state, independent commands in parallel; every PR is green on its own. Fix with `git commit --fixup=<sha>` on an unpushed commit, `<sha>` the commit that last changed those lines (a fix touching lines of two commits: one fixup per commit), else an ordinary commit.
   **Hand-over.** The context is large (about 100k tokens or more) after green checks: write a note to the scratchpad (branch, worktree path, spec link, check result, next step 6) and recommend `/clear`, then `/cj-implement <issue>` (plus the mode and `high` when it was given); step 2 resumes the linked branch without a PR. Small context: go on.

   **Review depth.** Set once before step 6 from the committed diff. Complexity is *high* when it touches money, data, security or an irreversible step, changes a condition under mutation check, or has 100 or more changed lines; else *low*. The argument `review:min` or `review:max` overrides. The report names the variant, its reason and its risk.

   **Model.** The bare argument `low` or `high` sets the model of reviewer and verifiers; neither given is `low`. Pass it to `cj-reviewing` as it came. No cost question is asked anywhere in the run. `low` is the orchestrator's model and effort, `high` is Opus with effort high, never weaker than the orchestrator. The argument is independent of `review:min` and `review:max`, in either order.

   | Variant | Step 6 | Step 7 | Risk |
   |---|---|---|---|
   | `min` | one reviewer, no second round | one verifier | one missed row or finding goes unseen; for typo or copy only |
   | recommended (default) | one reviewer, second round for production-code fixes | low: one verifier; high: two | a change rated low hides a real risk |
   | `max` | one reviewer, second round for every fix | two verifiers | highest token cost |

6. **Review.** Mandatory in every variant. Call the Skill tool with "cj-reviewing" and dispatch a fresh reviewer with the spec, the unit's AC and edge cases verbatim, the deviation comments, base, diff and check results. Fix legitimate findings the same way, rerun the affected checks, reject only with evidence. Production-code fixes get a second round, and a fix that touches a mutated condition reruns its mutation check. No reviewer available: report and stop before pushing.
7. **Verification.** The implementing agent never judges its own AC. Fresh subagents as the review depth says (one or two, two dispatched in parallel) with the model and effort settled in step 6, check the unit's final state, each in its own worktree on `HEAD` (`git worktree add --detach <path> HEAD`, removed afterwards). Each gets the same prompt: the spec, the unit's AC and edge-case rows verbatim, the deviation comments and the check commands; never the session history or the implementing agent's view of a row. Each changes nothing on the branch and returns per row its evidence (test name, check with result, or a manual check with its observation) and met or not met. "All tests green" covers nothing without its own test; a skipped test is missing. A row is met only when every verifier calls it met with evidence. A row only the open PR or a person can show (a CI run inside the PR, a state after merge, a release or device test, the user's own judgment) is **after-PR**: the verifiers name it with its reason, and it does not block the push. A row the PR shows is run right after step 9 and its Verified line updated; the rest stay `<row>: open, <who shows it>` for `/cj-accept`. A row not met: the implementing agent writes the missing test or the fix, reruns the affected checks (a production-code fix also gets a review round as in step 6), and the verifiers run again on the new state; a row still not met after that second round: report, no push. The two rounds count per unit, not per row: a row first reported not met in the second round gets no third round. Never change an expectation to match the code. No subagent available: report and stop before pushing. Checks red, findings open or an AC not met: report, no push. The rows every verifier met, with the mutation results from Build, become the Verified block of the PR body.
8. **Body.** Write the title and body as [PR-BODY.md](PR-BODY.md) says, and run its reading of the body against the diff. An unbacked claim, a test step or What bullet that breaks PR-BODY.md's rules, or a body over 20 lines stops here: no PR until the body, the diff or the unit's size is fixed.
9. **PR.** First `git fetch` and check the base again. Its PR merged since step 2: the default branch becomes the base; `git rebase --onto <remote>/<default branch> <that PR's head sha>`, drop the Stack line, and rerun the checks of step 5. The branch no longer merges cleanly into `<remote>/<base>` (`git merge-tree --write-tree <remote>/<base> HEAD` fails): rebase onto it, resolve, and rerun the checks. After a rebase here, read the repo's instructions again at the new base: a script or check the base gained since step 1 (a screenshot script, a new check) counts for this PR, and the body is read against PR-BODY.md once more before it opens. Then fold fixups of unpushed commits (`GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <upstream>`, `<upstream>` = `<remote>/<branch>` when pushed before, else `$(git merge-base HEAD <remote>/<base>)`). Save `<old-HEAD>` before the rebase, then run `git diff <old-HEAD> HEAD` as its own command, never chained to the push. Not empty: a fixup hit the wrong commit; `git reset --hard <old-HEAD>`, retarget, fold again. The fold stops on a conflict: `git rebase --abort`, then turn the conflicting fixups into ordinary commits with their own message; never squash the branch into one commit. Plain push only after an empty diff. Open the PR against the base with the checked title and body, or update its description; once that succeeded, set the review status as "Assignment and board status" says. Draft state and auto-merge follow "Small PRs and auto-merge". Review, checks and the Verified block are done before this step; an open finding or red check means no PR and no auto-merge.

After each PR: more ready units and the window still light, take the next; otherwise end with `/clear`, then `/cj-implement <issue>` (plus the chosen mode and `high` when it was given).

## 4. Report

Per PR: link, `Worktree: <absolute path> (branch <branch>)` again (acceptance by hand runs the change from there), draft or not, auto-merge on or off with the reason when it is off, base (stacked on which PR), verification table, checks, review outcome with the review depth variant, its reason and risk, the `Reviewer and verifiers: <model>, effort <effort>` line from `cj-reviewing`, the skip lines from "Assignment and board status". Then deviations, units left and why. Write it scannable: the first line is the result or the decision needed. Be extremely concise. Sacrifice grammar for the sake of concision. Text others read keeps full sentences. One sentence per bullet, at most 25 words. A list has 3 to 5 items, never more than 7; a longer one splits under two headings or goes onto a page. Three or more items go one per line, never inside a sentence. No nested lists, and no tables unless this skill names one; code, log and command blocks and the `Next:` block keep their own shape. Bold only as a label at the start of a line, code font for paths and commands. Headings name the topic in the reader's terms, not generic labels like Scope or Process. No made-up abbreviations: write glossary terms out unless the glossary defines the abbreviation as the term; code identifiers, paths and issue or PR numbers stay. Before the first question to the user, call the Skill tool with `cj-asking` and ask as it says. The verification table keeps its shape. The spec's **Acceptance line** decides whether `/cj-accept` comes: the last `Acceptance:` line of the latest `## Spec` comment, or of the issue body when it starts with `## Spec`. It reads `verified is enough`: verified is enough. A change that used the issue as its spec (step 1, no spec): verified is enough, and its deviations stay in this report. Anything else, a value this skill does not know or no line: by hand. Records wait when the spec's line reads verified is enough, a `## Challenge` comment holds a `**Kill criterion:**` line or the issue has a `Deviation:` comment, and no `## Acceptance` comment records them yet. Then the next step, first match wins: a ready ticket of this repo without a PR, or a fix-now row not done whose PR is still open: `/clear` + `/cj-implement <issue>` with the mode and `high` when it was given. A ticket in another repo without a PR, or one waiting on another repo: `/cj-implement <issue>` in that repo, with `high` when it was given, as step 2 says. Exactly one PR of the spec open, closing every ticket still open (the last stacked PR, the `one-pr` PR, a one-ticket spec's PR): by hand, `/cj-accept <issue>` with that PR's link and the worktree path, ahead of merging that PR, closing the spec's issue and `/cj-retro`, because acceptance runs before the last merge; records wait, the same line with `/cj-accept <issue>` for the records only; else merging that PR, closing the spec's issue, and `/cj-retro` only after a session with friction. Two or more PRs open: merge them in blocked-by order until one is left, then `/cj-implement <issue>` with the mode, which restacks and hands off. Every ticket merged: by hand with no `## Acceptance` comment that checked rows yet, fix-now rows left in it, or records wait, `/cj-accept <issue>`; else ask the user to close the spec's issue (or close it after their explicit yes) and run `/cj-retro`, with verified is enough only after a session with friction. Write the next step under a bold "Next:" (in the reply's language) as a numbered list, one command per line, each followed by ` · ` and its reason in a few words. A step that names a PR, issue or comment carries its full link, even when the link appears earlier in the reply. No table.

**Alternative line.** A run without `high` whose next step is a `/cj-implement <issue>` for a ticket without a PR adds one line below that step, the same command with the same `<issue>` (the spec's issue, as in that step) and `high` appended: `/cj-implement <issue> high · <reason>`. The reason names the risk in words (money, data, security or an irreversible step) when the Review depth rule above found it, else it reads "more findings outside the diff, more tokens". A run with `high` adds no such line, and neither does a next step for a ticket with an open PR.

## Small PRs and auto-merge

Auto-merge is **allowed** only when `conventions` explicitly allow it for small agent PRs. No mention, or a restriction ("no auto-merge", "only dependency bots"): not allowed, PRs are drafts and no merge command runs, whatever the size.

**Size** is read on the committed `HEAD` after `git fetch`: `git diff <remote>/<base> --shortstat`, insertions plus deletions, a missing part read as 0, tests and generated files counted, no path filter. Under 100 is **small**; 100 or more is not. `<base>` is the PR's own base.

- **Not allowed, not small, stacked** (the base is not the default branch), **or with an after-PR row** (step 7): draft, no merge command; a stacked PR would merge into its predecessor's branch, which neither closes its ticket nor has required checks. A repo without drafts gets a normal PR, as before.
- **Allowed and small:** open it not as a draft. After the push, `gh api repos/<repo>/branches/<base>/protection` must list required status checks; then run `gh pr merge <n> --auto --squash`. Not for the last PR of a spec whose Acceptance line is by hand (see the report step), meaning a PR after which no ticket of the spec is left without a PR, and every `one-pr` PR: acceptance runs before that merge, so it stays not-draft without auto-merge and the report names the reason.
- **No required checks** (the API answers 403 or 404, or lists none) **or the merge command fails:** the PR stays open, not a draft, without auto-merge. Run no direct merge. The report names the reason.
- **A later run pushes to a PR with auto-merge on** (`gh pr view <n> --json autoMergeRequest` is not null) **and the diff reaches 100 or more:** before the push, `gh pr merge <n> --disable-auto`, and `gh pr ready <n> --undo` where the repo has drafts. A small draft is never promoted.

## Assignment and board status

Only the issue the unit's branch is made from: the ticket in `per-ticket`, the spec's issue in `one-pr`. Never its parent, the other tickets, or anything in a fix-now run.

- **Assign** at the end of step 3.1: `gh issue view <n> --repo <its repo> --json assignees`, the user's login from `gh api user -q .login`. Someone else is assigned: stop before assigning and ask the user, naming them; the report names them too. Else `gh issue edit <n> --repo <its repo> --add-assignee @me`.
- **Look up the board** from the issue's own items; `gh issue view --json projectItems` returns no IDs, and no `gh project list` or `gh project item-add` runs:
  ```
  gh api graphql -f o=<owner of its repo> -f r=<name of its repo> -F n=<n> -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){issue(number:$n){projectItems(first:20){nodes{id status:fieldValueByName(name:"Status"){... on ProjectV2ItemFieldSingleSelectValue{name}} project{id title field(name:"Status"){... on ProjectV2SingleSelectField{id options{id name}}}}}}}}}'
  ```
- **Set the status** per board item: the one `Status` option whose name contains "progress", ignoring case and emoji, with `gh project item-edit --id <item> --project-id <project> --field-id <field> --single-select-option-id <option>`. Two or more such options: skip, ambiguous option. On a resumed branch only when the status is empty or contains "todo", ignoring case and emoji; a later status stays.
- **At PR open**, after `gh pr create` or the description update succeeded: the same lookup and `item-edit` for the one option containing "review", whatever the current status, also on a resumed branch. No such option: no change and no skip line; a skip line from the start is not repeated.
- **Skips.** A failed step skips only itself. The report gets one line per issue and board: `#<n> · <board title, or none>: <reason>`, each failed action on its own line and `none` for the assignment, the reason one of no board item, no `Status` field, no matching option, ambiguous option, no permission to assign. A lookup or `item-edit` error about the `project` scope reads `#<n> · none: missing project scope, run gh auth refresh -s project`, never "no board item".

## After a merge (per-ticket stacks)

After a squash merge git no longer recognises the merged PR's commits in the PR stacked on it, and GitHub may already have retargeted that PR to the default branch. Find each open PR of the spec whose description says `Stacked on #<P>` where #P is merged, then: `git fetch`, `git rebase --onto <remote>/<default branch> $(gh pr view <P> --json headRefOid -q .headRefOid) <ticket branch>`, `git push --force-with-lease`, `gh pr edit <n> --base <default branch>`, and drop the Stack line from its description. Only the ticket's own branch, never anyone else's. Step 2 runs this first.
