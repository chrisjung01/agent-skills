# Implement

Step 4 of the spec-driven flow, in every tier; a small change starts here with its issue as spec. Small PRs reach main faster and get better reviews, so the default is **one ticket, one branch, one draft PR**. Never merge. The one exception is a small PR in a repo whose `conventions` allow it: it opens not as a draft and the agent only switches auto-merge on; see "Small PRs and auto-merge".

## Mode

The argument after the issue picks the mode. No mode given and the spec has more than one ticket in this repo: ask once, before any branch, as a choice with three options where the harness offers one: "One PR per ticket (recommended)", "One PR for the whole spec" and "Stop before any branch", each with its consequence. One ticket, or fix-now rows from acceptance (step 2): no question; for fix-now rows the mode is the last PR's (a ticket checklist means `one-pr`). State the mode in the first line of the reply.

| | `per-ticket` (default) | `one-pr` (argument `one-pr`, "ein PR", "one PR") |
|---|---|---|
| PR unit | one ticket | all tickets of the spec in this repo |
| Branch | `gh issue develop <ticket>`, name `<prefix>/<ticket>-<slug>` | `gh issue develop <spec issue>`, name `<prefix>/<spec issue>-<slug>` |
| Base | the default branch; the open PR branch of its one unmerged blocker in this repo (stacked) | the default branch |
| Done state (resume) | per ticket: closed, or an open PR that closes it (its "Development" link can be missing) | the PR's ticket checklist |
| Links | `Closes #<ticket>`, `Part of #<spec issue>` | `Closes` for each done ticket of this repo, `Part of #<spec issue>` |
| When | the recommended answer | trying it out, or a wide refactor whose steps are not green on their own |

Call the Skill tool with "cj-project-context" for: commands, conventions, issue-tracker. Call the Skill tool with "cj-posting" before any outbound action. The user started this skill for PRs, so it carries the yes for the linked remote branches (`gh issue develop`), pushes to them, the PRs and their descriptions, switching auto-merge on or off as "Small PRs and auto-merge" says, deviation comments on the spec's issue, and the restack in "After a merge"; every other outbound action needs its own yes. When a situation tempts you to bend a step, check [WRONG-TURNS.md](WRONG-TURNS.md).

Keep a TODO list with the harness's task tool: one entry per PR unit, each with its steps. Before the final report nothing is open, or the report names it with the reason.

## 1. Read and gate

- Input: the spec's issue, or one of its tickets (then only that ticket).
- Read the issue, its latest `## Spec` comment (or its body, when the body starts with `## Spec`) and every comment after it (deviations, answers, the latest `## Acceptance` comment), the sub-issues with their blocked-by edges and state, the applicable `AGENTS.md`, the glossary and the ADRs the spec names, and the affected code. Call the Skill tool with "cj-static-analysis" for the callers of the symbols the change touches; each unit asks again in its worktree before Build.
- **No spec** (no `## Spec` comment, no body starting with `## Spec`). A trivial change (typo, copy, a one-line fix whose expected behaviour the issue states) may use the issue as its spec: say so in one line and go on with its criteria as AC-1… Anything else: stop and name `/cj-grill-with-docs <issue>` and `/cj-to-spec <issue>`.
- The spec has an open question, or a criterion you cannot verify: stop and ask. Code or docs answer facts; only product decisions go to the user.
- No sub-issues (the spec fits one ticket): the spec's issue is the one ticket; both modes give one PR. Leave its title unchanged, including any existing `[Epic] ` prefix. The PR only `Closes #<issue>`, without `Part of`.

## 2. Pick the work

First restack what "After a merge" describes. Then, per ticket of this repo, and for the spec issue in `one-pr`: `gh issue develop --list <n> --repo <its repo>`, and once `gh pr list --repo <its repo> --state open --json number,headRefName,closingIssuesReferences`; skip what the mode's done state marks as done. A linked branch without a PR is an interrupted run: `git fetch`, then continue in the worktree `git worktree list` shows for it, else `git worktree add <path> <branch>` as in step 3.1; never run `gh issue develop` for it again.

**Fix-now rows.** The latest `## Acceptance` comment has rows whose choice is fix now: they are this run's only PR unit, on the last open PR the comment names. Each row is an AC of the unit, the user's observation its bug report. `git fetch`, then continue on that PR's branch in the worktree `git worktree list` shows, else `git worktree add <path> <branch>`; never `gh issue develop`. Fast-forward it to `<remote>/<branch>`; diverged: stop and report. Run step 3 from Build on, a failing test first, written as Build says for a bug when the row describes one; step 8 replaces the row's earlier Verified line with one that cites the comment, `<row> (acceptance <comment link>): <evidence>, met`, rows with the same evidence sharing a line. A row is done, and skipped, once the Verified block cites that comment for it. That PR already merged: build nothing; `/cj-accept <issue>` turns the rows into follow-ups.

A ticket is **ready** when every blocker is closed, or (per-ticket) exactly one blocker is open, is in this repo and has an open PR, including one opened earlier in this run: that PR's branch becomes the base. In `one-pr`, a blocker inside the same unit counts as done once its commits are on the branch. A blocker in another repo that is still open, or two open blockers: not ready; the report says why and names `/cj-implement` in the other repo.

Done when you can state the PR units of this run, in blocked-by order, with the base of each.

## 3. Per PR unit

Finish one unit completely, PR included, before the next.

1. **Branch** through the issue the mode names, so it is linked under "Development": `gh issue develop <n> --repo <its repo> --branch-repo <this repo> --base <base> --name <name>` (prefix from `conventions`, else `agent/`). Check it out in its own worktree: `git fetch` and `git worktree add <path> --track -b <branch> <remote>/<branch>`, `<path>` from `conventions`, else the harness's, else a sibling directory of the checkout; the user's checkout only when they ask for it. Then tell the user once: `Worktree: <absolute path> (branch <branch>)`. `HEAD` equals `<remote>/<base>` before the first change. Never overwrite, discard or stash the user's uncommitted changes. The first unit of a spec also commits the glossary or ADR files the spec lists under "Recorded in repo"; the report tells the user to delete uncommitted originals in their checkout.
2. **Build** each ticket of the unit in blocked-by order. Tests first at the spec's seams where the project allows it. For a bug (a bug ticket, or a fix-now row that describes one), a fresh subagent writes the reproduction test before any fix; its prompt holds the repo and the report's symptom, steps, expected and actual result (for a fix-now row, the row and the user's observation), never a diagnosis or a fix, so suspected lines, code paths, proposed fixes and suggested tests in the issue stay out. The test is red before the fix; green means the bug is not reproduced: stop and report. No subagent available: write it yourself, and the PR's Risk line says so. Targeted tests and typechecks while working. Commit per finished step, self-contained, tests with the logic they cover, the repository's message convention, the ticket number in the message. **Mutation check**, for every AC test that covers a condition the diff adds or changes: on a clean, committed tree invert that condition once, run the test, restore; afterwards `git status` is clean again. The test must turn red. Green: a test is missing; write it before the PR and invert again. No input tells the inverted condition apart: the condition is dead; remove it instead. ACs without such a condition, such as copy or layout, get none.
3. **Size.** Over about 400 changed lines without tests and generated files: the ticket was cut too big. Say so and propose a split before going on; a preparatory refactoring becomes its own ticket.
4. **Deviations.** A technical decision that differs from the spec (interface, order, a module): a comment on the spec's issue, `Deviation: <decision> | <reason> | <cost if wrong>`, and continue. A change to behaviour, scope or an AC: stop and ask. On a yes, edit the spec comment as `cj-to-spec` describes under "Changing a posted spec" (that yes covers the edit).
5. **Checks.** The full required checks once on the unit's final state, independent commands in parallel; every PR is green on its own. Fix with `git commit --fixup=<sha>` on an unpushed commit, `<sha>` the commit that last changed those lines, else an ordinary commit.
6. **Review.** Mandatory. Call the Skill tool with "cj-reviewing" and dispatch a fresh reviewer with the spec, the unit's AC and edge cases verbatim, the deviation comments, base, diff and check results. Fix legitimate findings the same way, rerun the affected checks, reject only with evidence. Production-code fixes get a second round, and a fix that touches a mutated condition reruns its mutation check. No reviewer available: report and stop before pushing.
7. **Verification.** Per AC and edge-case row of the unit: evidence from the final state (test name with its mutation result, check with result, or a manual check with its observation) and met or not met. "All tests green" covers nothing without its own test; a skipped test is missing; never change an expectation to match the code. Checks red, findings open or an AC not met: report, no push. These lines become the Verified block of the PR body.
8. **Body.** Write the title and body as [PR-BODY.md](PR-BODY.md) says, and run its reading of the body against the diff. An unbacked claim or a body over 15 lines stops here: no PR until the body, the diff or the unit's size is fixed.
9. **PR.** Fold fixups of unpushed commits (`GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <upstream>`, `<upstream>` = `<remote>/<branch>` when pushed before, else `$(git merge-base HEAD <remote>/<base>)`). Save `<old-HEAD>` before the rebase, then run `git diff <old-HEAD> HEAD` as its own command, never chained to the push. Not empty: a fixup hit the wrong commit; `git reset --hard <old-HEAD>`, retarget, fold again. Plain push only after an empty diff. Open the PR against the base with the checked title and body, or update its description; draft state and auto-merge follow "Small PRs and auto-merge". Review, checks and the Verified block are done before this step; an open finding or red check means no PR and no auto-merge.

After each PR: more ready units and the window still light, take the next; otherwise end with `/clear`, then `/cj-implement <issue>` (plus the chosen mode as argument, so the next run does not ask again).

## 4. Report

Per PR: link, draft or not, auto-merge on or off with the reason when it is off, base (stacked on which PR), verification table, checks, review outcome. Then deviations, units left and why. Write it scannable: the first line is the result or the decision needed. One sentence per bullet, at most 25 words. A list has 3 to 5 items, never more than 7; a longer one splits under two headings or goes onto a page. Three or more items go one per line, never inside a sentence. No nested lists, and no tables unless this skill names one; code, log and command blocks and the `Next:` block keep their own shape. Bold only as a label at the start of a line, code font for paths and commands. Headings name the topic in the reader's terms, not generic labels like Scope or Process. No made-up abbreviations: write glossary terms out unless the glossary defines the abbreviation as the term; code identifiers, paths and issue or PR numbers stay. Before the first question to the user, call the Skill tool with `cj-asking` and ask as it says. The verification table keeps its shape. The spec's **Acceptance line** decides whether `/cj-accept` comes: the last `Acceptance:` line of the latest `## Spec` comment, or of the issue body when it starts with `## Spec`. It reads `verified is enough`: verified is enough. A trivial change that used the issue as its spec (step 1, no spec): verified is enough, and its deviations stay in this report. Anything else, a value this skill does not know or no line: by hand. Records wait when the spec's line reads verified is enough, a `## Challenge` comment holds a `**Kill criterion:**` line or the issue has a `Deviation:` comment, and no `## Acceptance` comment records them yet. Then the next step, first match wins: a ready ticket of this repo without a PR, or a fix-now row not done whose PR is still open: `/clear` + `/cj-implement <issue>` with the mode. A ticket in another repo without a PR, or one waiting on another repo: `/cj-implement <issue>` in that repo, as step 2 says. Exactly one PR of the spec open, closing every ticket still open (the last stacked PR, the `one-pr` PR, a one-ticket spec's PR): by hand, `/cj-accept <issue>` with that PR's link, ahead of merging that PR, closing the spec's issue and `/cj-retro`, because acceptance runs before the last merge; records wait, the same line with `/cj-accept <issue>` for the records only; else merging that PR, closing the spec's issue, and `/cj-retro` only after a session with friction. Two or more PRs open: merge them in blocked-by order until one is left, then `/cj-implement <issue>` with the mode, which restacks and hands off. Every ticket merged: by hand with no `## Acceptance` comment that checked rows yet, fix-now rows left in it, or records wait, `/cj-accept <issue>`; else ask the user to close the spec's issue (or close it after their explicit yes) and run `/cj-retro`, with verified is enough only after a session with friction. Write the next step under a bold "Next:" (in the reply's language) as a numbered list, one command per line, each followed by ` · ` and its reason in a few words. A step that names a PR, issue or comment carries its full link, even when the link appears earlier in the reply. No table.

## Small PRs and auto-merge

Auto-merge is **allowed** only when `conventions` explicitly allow it for small agent PRs. No mention, or a restriction ("no auto-merge", "only dependency bots"): not allowed, PRs are drafts and no merge command runs, whatever the size.

**Size** is read on the committed `HEAD` after `git fetch`: `git diff <remote>/<base> --shortstat`, insertions plus deletions, a missing part read as 0, tests and generated files counted, no path filter. Under 100 is **small**; 100 or more is not. `<base>` is the PR's own base.

- **Not allowed, not small, or stacked** (the base is not the default branch): draft, no merge command; a stacked PR would merge into its predecessor's branch, which neither closes its ticket nor has required checks. A repo without drafts gets a normal PR, as before.
- **Allowed and small:** open it not as a draft. After the push, `gh api repos/<repo>/branches/<base>/protection` must list required status checks; then run `gh pr merge <n> --auto --squash`. Not for the last PR of a spec whose Acceptance line is by hand (see the report step), meaning a PR after which no ticket of the spec is left without a PR, and every `one-pr` PR: acceptance runs before that merge, so it stays not-draft without auto-merge and the report names the reason.
- **No required checks** (the API answers 403 or 404, or lists none) **or the merge command fails:** the PR stays open, not a draft, without auto-merge. Run no direct merge. The report names the reason.
- **A later run pushes to a PR with auto-merge on** (`gh pr view <n> --json autoMergeRequest` is not null) **and the diff reaches 100 or more:** before the push, `gh pr merge <n> --disable-auto`, and `gh pr ready <n> --undo` where the repo has drafts. A small draft is never promoted.

## After a merge (per-ticket stacks)

After a squash merge git no longer recognises the merged PR's commits in the PR stacked on it, and GitHub may already have retargeted that PR to the default branch. Find each open PR of the spec whose description says `Stacked on #<P>` where #P is merged, then: `git fetch`, `git rebase --onto <remote>/<default branch> $(gh pr view <P> --json headRefOid -q .headRefOid) <ticket branch>`, `git push --force-with-lease`, `gh pr edit <n> --base <default branch>`, and drop the Stack line from its description. Only the ticket's own branch, never anyone else's. Step 2 runs this first.
