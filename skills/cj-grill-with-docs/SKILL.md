# Grill with docs

Step 1 of the spec-driven flow. It settles the tier first: the big tier gets the challenge (step 0) before any grilling question, the small tier goes straight to `/cj-implement`. It ends in a shared understanding, not in code or a spec.

1. **Input.** An issue reference: read the body, every comment, linked issues and the affected code. Call the Skill tool with "cj-static-analysis" for the callers of the symbols the change touches. An idea without an issue: start from the user's words.
2. **Tier.** Settled already: the latest `## Challenge` comment, the latest `Tier: <tier>, confirmed` line on the issue, from any comment, or a challenge result earlier in this session. Then ask no tier question and run no challenge. A challenge verdict and its smaller lever are settled decisions; a verdict other than "build" or "build differently" ends the run with that verdict's next step from [CHALLENGE.md](CHALLENGE.md). Exception: the latest `## Challenge` comment blocks and a later comment documents the gap; the block reopened, so run the challenge again and post a new `## Challenge` comment.
   Not settled: the first question proposes a tier, names the signs found, and offers the other two tiers as options.
   - **Big** when the change touches money, data, security, an irreversible step, or needs real effort or more than one ticket.
   - **Small** for a typo or copy change, a fix that restores behaviour the issue states as intended (length alone does not disqualify it), or a refactor whose issue states its scope and unchanged behaviour, none with an open product decision.
   - **Normal** for anything else, including a new rule the issue calls a fix.

   Money, data, security or an irreversible step, judged by what the change touches and not by words in the issue, beats small unless the user confirms small; real effort and more than one ticket are further big signs and also win over small.

   Write it scannable: the first line is the result or the decision needed. Be extremely concise. Sacrifice grammar for the sake of concision. Text others read keeps full sentences. One sentence per bullet, at most 25 words. A list has 3 to 5 items, never more than 7; a longer one splits under two headings or goes onto a page. Three or more items go one per line, never inside a sentence. No nested lists, and no tables unless this skill names one; code, log and command blocks and the `Next:` block keep their own shape. Bold only as a label at the start of a line, code font for paths and commands. Headings name the topic in the reader's terms, not generic labels like Scope or Process. No made-up abbreviations: write glossary terms out unless the glossary defines the abbreviation as the term; code identifiers, paths and issue or PR numbers stay. Before the first question to the user, call the Skill tool with `cj-asking` and ask as it says. The user's tier holds, also when it differs from the proposal. Big: run [CHALLENGE.md](CHALLENGE.md) now, before any grilling question; it posts the verdict as a `## Challenge` comment, or where the user picks for an idea without an issue. "Build" or "build differently": grill on in this run. Normal: no challenge question and no hint to run one. Small: no grilling question. An issue that would serve as its own spec (no feature) with one of those four stakes first gets a comment holding the line `Tier: small, confirmed`, posted through `cj-posting`, unless its latest `Tier:` line already reads small; without such a stake nothing is posted. The next step is `/cj-implement <issue>`, for an idea without an issue filing the issue first (call the Skill tool with "cj-filing-issues").
3. **Grill.** Call the Skill tool with "cj-grilling". Facts come from code, docs and tools; only decisions go to the user. Normal tier, and an answer brings up money, data, security or an irreversible step: the next question proposes the big tier again; on a yes, run [CHALLENGE.md](CHALLENGE.md) before the next grilling question; a verdict other than "build" or "build differently" ends the run with that verdict's next step. More than one ticket alone proposes nothing.
4. **Questions only the issue author can answer** (product intent, a business rule nobody in the session owns): collect them into one comment on the issue, numbered, each with a proposed answer, plus the line `Tier: <tier>, confirmed`. Call the Skill tool with "cj-posting" before posting it. Stop there. When the answers arrive (even days later), the user starts `/cj-grill-with-docs <issue>` again: it reads the answers from the thread as settled decisions and grills only what is still open.
5. **Close.** List every decision, plus the glossary terms and ADRs written during the session (left uncommitted; `cj-to-spec` lists them, `cj-implement` commits them on the feature branch). Write it scannable: the first line is the result or the decision needed. Be extremely concise. Sacrifice grammar for the sake of concision. Text others read keeps full sentences. One sentence per bullet, at most 25 words. A list has 3 to 5 items, never more than 7; a longer one splits under two headings or goes onto a page. Three or more items go one per line, never inside a sentence. No nested lists, and no tables unless this skill names one; code, log and command blocks and the `Next:` block keep their own shape. Bold only as a label at the start of a line, code font for paths and commands. Headings name the topic in the reader's terms, not generic labels like Scope or Process. No made-up abbreviations: write glossary terms out unless the glossary defines the abbreviation as the term; code identifiers, paths and issue or PR numbers stay. Before the first question to the user, call the Skill tool with `cj-asking` and ask as it says. Show the list in the reply text, never as a prose paragraph and never only inside the `Next:` block, decisions numbered so the user can name one. The coverage table from `cj-grilling` stands above the numbered list in this same reply; this list is the grilling summary, so the user sees one summary, not two. Ask no confirm question: the `Next:` block follows the list in this same reply, and one line above it says that running its command confirms every decision and that a reply naming a decision number with its change ("2 streichen") changes or drops that decision. Running the command is the confirmation `cj-grilling` waits for, and the close counts as no question of a question series. A reply that changes a decision, by number or in words, gets the updated list and the `Next:` block again; a reply that only agrees ("passt") gets the command again in one line, without a question.

Done when the frontier is empty and the closing reply ends with the next step: `/cj-to-spec <issue>` now, in this session, without `/clear` first, because spec and tickets are cut from this conversation. A run that step 2 or 3 ends (small tier, or a verdict that stops) ends with that step's next step instead. Write the next step under a bold "Next:" (in the reply's language) as a numbered list, one command per line, each followed by ` · ` and its reason in a few words. A step that names a PR, issue or comment carries its full link, even when the link appears earlier in the reply. No table.
