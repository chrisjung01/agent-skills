# Lint from findings

A mistake a linter could have caught comes back in the next PR unless a check stops it. This skill turns each mechanical finding into the cheapest check that holds, proves the check fires, and lets the user decide where it goes. The caller passes the findings (`id, location, title, problem`) and per finding the commit that fixed it, `uncommitted`, or `none`.

Call the Skill tool with "cj-project-context" for: commands, standards, conventions.

## Steps

1. **Filter.** Keep a finding only when a check can spot it in the source text without knowing intent: a banned API or import, an import shape, a file in the wrong place, a fixed code pattern. Smells and judgement calls drop out; they belong in the standards file. So does a rule that would catch only this one instance (one banned name), not the class of mistake. Nothing left: say "nothing to mechanize" in one line and stop, without a question.
2. **Inventory.** From `commands` and `standards`: the linters, their config files, the lint command, whether it fails on warnings, and the hook or CI step that runs it. Run the check-only form of the lint command (never a fix or format variant) once on each finding's source file as it is today (a file-location finding: the file at its new path, none when the fix deleted it; a linter that only takes a whole package: its package). That run is the baseline step 4 judges a source against. When it does not run (missing dependencies, unknown command, a config that does not load), name the error, offer every finding as an issue, and never install dependencies in the caller's checkout to make it run. No linter: every finding starts at rung 3.
3. **Draft** on the first rung that holds:
   1. a rule the installed linter already has, enabled or configured
   2. a generic pattern rule of that linter (restricted imports, restricted syntax, banned API) with the finding's pattern
   3. a grep script in the repo's script folder, run by the hook or CI step that runs the repo's checks (`commands`); with none, the diff adds a CI step or a pre-commit entry for it, and step 5 says so
   4. a custom plugin rule: draft no code; it becomes an issue draft in step 5
4. **Prove** in the working tree, with no second source file, and leave nothing behind. The faulty version (the probe) sits in the original file, the only path with its namespace, module entry and path-scoped config.
   1. Note `git status --short --ignored` and `git diff HEAD | git hash-object --stdin`. Copy every file the proof will touch (lint config, hook, CI file, the finding's source file, for a file-location finding the file at its new path) to a scratch folder outside the repo, and name each copy's path in the chat before the first write, written as step 5 says.
   2. Before every write to a touched file, compare its hash with what you last wrote there, or with its saved copy before the first write; a file that did not exist must still not exist. A difference: write nothing more, stop, and name the changed file and every saved copy's path, written as step 5 says; this is the one stop that leaves the edit in place, for the user to restore from those copies.
   3. Add the rule, or write the rung-3 script.
   4. Put the probe at the original path. A file-location finding moves the file back to its path before the fix, never copies it; a file the fix deleted comes back from the source. A committed fix whose changed lines in today's file hold the finding's faulty code again (what `<fix>^` had there, not just a name the fix kept; a revert, or a later edit that brings it back) means fix `none`, whatever the caller passed; never asked of `uncommitted` or a file-location finding; for `none` the finding's lines are where today's file holds that code, and nowhere means "not proven". A file-location finding whose fix only moved the file takes today's content. Sources, in order: today's file with only the fix undone (for a commit, a three-way merge that applies the step from the fix back to its parent onto today's file: `git merge-file -p <today> <file at fix> <file at fix^>`, files from `git show` into the scratch folder, a rename read at both paths after the move (the old path from `git show -M --name-status <fix>`), a file the fix added or deleted as an empty file; a conflict means the source does not apply. For `uncommitted`, each hunk of `git diff -U0 HEAD -- <path>` whose old-side lines hold the code the finding names (a hunk that only adds, `-N,0`: the one placed right at that code) gets its old-side lines back at its new-side position in today's file (`+N,M` replaces lines N to N+M-1, a missing M is 1, `+N,0` inserts after line N), the hunk furthest down first; no such hunk: the source fails. For `none`, today's file unchanged), the whole file before the fix (`git show <fix>^:<path before the fix>`, `HEAD` for `uncommitted`), the code quoted in the finding in place of the finding's lines, code written from the finding text in the same place. A source fails when it does not exist or does not apply, when it does not hold the code the finding names at the probe lines (not asked of a file-location finding), or when the first run shows errors other than this rule's that the step 2 run did not (no step 2 run: any error), config or rule-option errors excepted, without reporting this rule at the probe lines; take the next one, built again from the saved copy.
   5. First run: the check-only form of the lint command (never a fix or format variant), or the rung-3 script, on that one file; a linter that only takes a whole package lints its package, and only hits in that file count. It must report this rule at the probe lines: the finding's lines in the probe (a file-location finding: the file).
   6. Put the corrected version at the original path: the saved copy, or for fix `none` today's file corrected only at the finding's lines; a file-location finding moves the file to its new path, or removes it when the fix deleted it. Second run, over the whole repo: a hit of this rule at the lines the fix changed, counted in today's file (fix `none`: the corrected lines), means the rule fires on the fix; every other hit of this rule counts toward the hit total, and for fix `none` so do the first run's hits at the finding's lines, since today's file still holds them.
   7. Save the rule's change (config, hook, CI file, script) as a diff against the saved copies (not against `HEAD`, which would carry earlier uncommitted edits), with new files in full. Delete new files and copy the saved files back. Both notes from 4.1 match again and each touched file is byte-identical to its copy (`cmp`); a difference is fixed before anything else.

   A draft attempt makes one first run per source tried and one second run, never more; the step 2 run and the path question below are not counted. Every source failed, or a corrected version for fix `none` whose file shows errors other than this rule's that the step 2 run did not: restore, the finding is "not proven" and offered as an issue, never a rung drop. The first run reports this rule nowhere at the probe lines and the source did not fail: ask the linter whether it lints that path (its file list or debug output); not linted or unclear: restore, the finding is "not proven", and only a path shown to be linted makes the rule drop one rung; either way, decide before a second run. A rule that fires on the fix drops one rung. The lint run errors on the config or the rule's options (unknown rule, bad options): the draft is at fault, never a path question; restore (4.7), then fix the draft as a new draft attempt or drop a rung, and never stop with the edit in place except at a 4.2 stop. A rung drop first restores (4.7) and checks the notes, then starts the next draft attempt at 4.1, which keeps existing saved copies and adds the files the new draft will touch. Several findings in one file: each proof starts from the restored file.
5. **Show.** Everything the user reads goes through the `unslop` skill. Write it scannable: the first line is the result or the decision needed. One sentence per bullet, at most 25 words. A list has 3 to 5 items, never more than 7; a longer one splits under two headings or goes onto a page. Three or more items go one per line, never inside a sentence. No nested lists, and no tables unless this skill names one; code, log and command blocks and the `Next:` block keep their own shape. Bold only as a label at the start of a line, code font for paths and commands. Headings name the topic in the reader's terms, not generic labels like Scope or Process. No made-up abbreviations: write glossary terms out unless the glossary defines the abbreviation as the term; code identifiers, paths and issue or PR numbers stay. Before a question, the reply text holds the full list with details, numbered; with nothing to list, one line of context is enough. A question has 3 options, a fourth only as a real alternative, the recommended one first; with only one real option, the proposal and something else. Each option names its item and says in full words what it means and its one consequence, so the user decides without scrolling up. Ask the question through the harness's choice tool where one exists, with the list in the reply text above it, never as options typed into the reply; without a choice tool, number the options 1), 2), 3). Per finding, numbered: its title, the rung and rule, the diff, and the line `fires on probe, fix clean, <N> hits in repo`. With N > 0, list the hits as `file:line`, at most 10, then the count of the rest. Rung 4 and unproven findings show the issue draft instead.
6. **Ask** one question per finding, as a choice, naming the finding by its number and a few words:
   - **own PR** (recommended): the rule at `error` in a new worktree from the default branch, at the path from `conventions`; the caller's checkout stays as it is. With N from 1 to 10 the PR also fixes the hits; with more, the option names the count and the cleanup becomes an issue, so the rule waits for it. When the lint command ignores warnings, the option may land the rule at `warn` instead: it shows the hits and blocks nothing new. A rung-3 script with N > 0 checks only the files a change touches.
   - **current branch**: the rule lands on the caller's branch the way the caller lands its own fixes: uncommitted when they stay uncommitted; a commit when the caller commits them, then a push question through `cj-posting`, because the caller's own push may be past. Not offered when the caller has no branch of its own (a retro). With N > 0 only at `warn` and only when the lint command ignores warnings; otherwise this option is not offered, because the hits would make the branch fail its own check.
   - **issue**: call the Skill tool with "cj-filing-issues", the diff and the proof line in the body.
   - **drop**.

   Rung 4 and unproven findings get two options, issue (recommended) and drop; this overrides the three-option rule above.
7. **Do what got a yes.** Own PR: set up the new worktree as `commands` set up a fresh checkout, re-apply the rule there (by hand when the diff does not apply), and run the lint command again; a hit count other than the proof's goes to the user before the commit. Then branch, commit and open a draft PR by `conventions` (a normal PR where the repo has no drafts). Call the Skill tool with "cj-posting" before any push, PR or issue.

Done when every mechanical finding has its rule applied, an issue, or a no, and the working tree holds only what got a yes, or a 4.2 stop named the saved copies.
